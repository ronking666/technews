# 早上 7 点前收报：外部定时触发

用户选择免费外部定时服务触发 GitHub，目标为北京时间每天 07:00 前收到科技和财经早报。现有运行日志显示 GitHub schedule 在创建运行记录之前延迟数小时，而程序执行通常不到一分钟。

## Approaches

- **已选择：cron-job.org 调用 GitHub workflow_dispatch**。保留现有 Python 程序、GitHub Secrets 和执行环境，改动少；仍依赖外部定时服务、GitHub 执行资源和微信推送链路，无准点保证。
- 云函数直接运行：同时绕过 GitHub 定时与执行，需新云账号、部署与计费设置。
- 电脑定时运行：无需云账号，但依赖电脑在清晨开机联网。

## 具体行为

- 外部定时服务为两份日报各建一个任务，时区 Asia/Shanghai，每天 06:40 和 06:50 发起启动请求，后一次用于失败补发。
- 保留两个现有 GitHub 凌晨 schedule 作为兜底：科技北京时间 04:27，财经纽约 16:47。外部服务未启用或故障时不把原有调度时间推迟；这些触发仍可能在数小时后才执行。
- 同一报告的所有触发来源共用现有并发组，串行执行、不取消已经开始的任务。
- 发送前检查当天北京时间对应的成功回执 artifact；已成功发送则跳过抓取、AI 和推送。
- 仅默认分支可发送。回执只信任本仓库、默认分支创建的 artifact。
- 推送步骤成功后上传一个不含报告正文或密钥的回执，保留 7 天。发送失败不创建回执，允许下次重试。
- 查询回执失败时停止发送，避免把未知状态当作未发送。GitHub token 只注入检查步骤；报告服务密钥只注入发送步骤。
- 北京时间 23:45 起停止新发送，为工作流 10 分钟超时留出跨日余量；次日可恢复，清晨任务不受影响。
- 日志记录北京时间、报告类型和跳过/发送决定。提供已填写仓库地址和时间的配置示例、启用步骤和人工验收方法。

## 边界

- 本次不创建外部账号，不在聊天或文件中收集密钥，不自动触发真实微信推送。
- 两份报告按北京时间的发送日期独立去重；休市日仍遵循现有行情处理。
- 本方案不是端到端 exactly-once：发送被接收、但回执上传失败或流程被终止时，重试仍可能重复；超时也可能导致送达状态不明。该限制须在启用说明中明确。
- API 接受触发请求只表示已接受启动，不代表日报已生成或微信已送达。需检查 GitHub 发送步骤和回执。
- 外部服务尚未启用时，原有凌晨 schedule 仍照常运行且可能延迟。

## 验证

测试同一天不同报告独立处理、北京时间跨日、成功回执跳过、过期/其他日期/其他分支/其他仓库回执不影响发送、API 错误停止发送且不泄露 token。验证工作流的发送与回执条件、时区、并发和权限。运行完整 pytest 和 Ruff；不使用真实推送测试。
